# The Ever-Unfolding Saga

## Roadmap

The roadmap tracks current and upcoming development. Detailed completed milestone history is kept in [`docs/roadmap-history.md`](docs/roadmap-history.md). The intended product direction is recorded in [`docs/design-principles.md`](docs/design-principles.md); this roadmap distinguishes those long-term goals from what is currently implemented and validated.

## Current state

The v0.52.0–v0.52.6 storage, mod-management, and character-focused interface work is complete and recorded in the roadmap history. Spatial exploration and interaction are now the active development line. PR #404 implements persistent spatial actors, contextual action/target resolution, and the modular portrait catalogue. Its implementation commit passed automated checks, but desktop and Android landscape playtesting remains outstanding. The player-anchored radial interaction wheel adapts to landscape viewport dimensions, adds a second ring for crowded targets, and animates selected-entry feedback. Shared scene transitions and the dedicated close-up dialogue presentation from #405 have been manually play-tested by the project owner. The player now configures a persistent portrait during new-character creation, while NPC portraits retain deterministic weighted generation; the spatial interaction control identifies its nearby target before opening that target's action list.

## Spatial-first gameplay direction

The current Gameplay dashboard is a transitional hub, not the intended permanent gameplay surface. Issue #421 tracks the migration of its useful functions—world context, travel, Explore/Investigate, meditation, character records, and system/menu access—into discoverable spatial HUD controls, contextual interactions, overlays, and focused record screens. The dashboard must remain available until those functions have replacements that work on desktop and Android landscape. The spatial scene should remain the primary context when opening and closing ordinary overlays where appropriate; safe-location activities must remain convenient rather than requiring unnecessary movement. The dashboard/pause function audit and proposed spatial placements are recorded in [the spatial-first function map](docs/systems/spatial-first-migration.md). The existing unified pause menu is accessible over spatial exploration through desktop Escape and Android Back; dismissing it restores the same spatial session. Destination-list travel is available from that menu and enters the destination's spatial map. Meditate appears in the same menu only when safe, opening the existing meditation flow and returning to the paused spatial scene. New character creation, inheritance, and successful save loading now hand off directly to spatial exploration. Leave remains a separate, explicit transition to the compatibility dashboard.

The first foundation refinement makes movement collision checks resilient to brief frame drops and makes camera smoothing frame-rate independent while enforcing map bounds after smoothing. The reusable spatial sprite-animation layer now defines four directional idle/walk clips, frame-rate-independent playback, and a mod-aware sprite-sheet contract with a static-sprite fallback while the art is pending. Dedicated screens now retain their invoking screen as a return target, and the spatial scene requests a presentation rebuild when navigation returns to it; the existing map and continuous position remain in the spatial state. The directional player sheet is currently an empty placeholder; visible directional animation is not complete until valid 80×96 artwork is supplied and verified in-game. This is an incremental foundation pass, not a claim that the spatial-first migration is complete.

## Developer tools

**v0.52.21 — Developer tools: World Lab authoring completion (#413)**

The start screen exposes a Developer Tools hub without requiring a campaign or save. Character Workshop manually assembles loaded modular portrait parts, previews them through the same layered portrait compositor and mod-aware PNG loader used by dialogue, and supports per-slot selection, visibility toggles, deterministic randomization, reset, and diagnostics. This remains a portrait-focused tool, not a full-body character editor.

World Lab generates reproducible temporary local maps from a deterministic, disposable world graph and uses the same spatial generator and gameplay renderer as exploration. Its editor supports validated terrain changes; pillar/table placement, movement, and removal; temporary point-of-interest placement, movement, and removal; physical passage placement, movement, and removal; and actor placement, movement, and removal. Passage destinations are selected from real locations in the generated world graph, and edits update reciprocal graph links. Actor placements reference actual generated NPC/remains entity identities and never invent entity IDs. Placement validation protects entries, walkable paths, discoveries, passages, actors, and prop footprints from conflicting edits. Maps can be play-tested through the production spatial renderer, movement/collision, depth ordering, camera follow, and Android virtual joystick; edits survive returning to the editor and remain isolated from campaign state and saves. Versioned JSON fixtures preserve complete LocalMap state, can be imported/exported through desktop and Android document pickers, and are validated before loading. Fixture restoration reconstructs the deterministic world graph and actor catalogue from the saved seed, retaining only passage and actor references that still resolve. Fixtures use a dedicated developer-fixtures directory and import inbox, never campaign save slots; invalid files remain visible with diagnostics.

Character Workshop manually assembles currently available modular portrait parts using the same gameplay compositor and mod-aware asset loader as dialogue. It supports per-slot selection, visibility toggles, deterministic randomization, reset, and diagnostics. This completes the initial developer-tools scope; full-body character authoring is not a prerequisite because the required full-body visual assets and renderer do not yet exist. Future Character Workshop expansion can be tracked separately when those systems arrive.

## Active milestone

**v0.52.31 — Spatial exploration foundation and context-preserving navigation** (prototype #353; actor and interaction foundation #404; presentation follow-up #405; world-topology design #365)

The renderer-neutral local-map model, deterministic generation, Bevy exploration view, continuous movement, blocked-terrain collision, camera tracking, depth ordering, and world-persistent map state are implemented. The prototype includes desktop keyboard movement, an Android virtual joystick, first-pass pixel-art terrain and character assets, basic prop collision and occlusion, and the authored Old Shrine chamber layout (#381). The exact active exploration position and session remain character-specific, while established local maps and their lasting changes persist with the world.

PR #404 extends Explore to safe and dangerous locations and removes detached Talk and Search Remains dashboard actions. NPCs and searchable remains receive deterministic placements on reachable map cells and persist with their local maps; older saves receive safe defaults until a map is first entered. Nearby NPCs, remains, points of interest, and passages resolve into stable action/target pairs through renderer-neutral discovery in `interaction_actions.rs`; the Bevy adapter consumes those results rather than owning proximity, line-of-sight, actor-state, and inventory eligibility rules. The player-anchored radial action wheel presents every eligible pair, adapts to available landscape space, uses a second ring when nearby targets crowd the first, and gives selection changes a brief eased pulse. Directional keyboard selection and Android touch activation use the visible entry positions, and selected identities are revalidated before dispatching the existing Talk, Search Remains, Examine, or Enter behavior. New local maps can also receive multiple deterministic, campaign-authored points of interest; they remain hidden until their map tiles are explored, then appear as world markers and eligible Examine actions. Their reveal and examination state persists with the local map, and mods can extend or override definitions by stable ID. NPC dialogue now transitions into a dedicated close-up scene showing the player and NPC together. The player's portrait is composed from stable, player-selected body, face, hair, headgear, and accessory part IDs configured during new-character creation; NPC portraits continue to use deterministic weighted selection from the same mod-extensible catalogue. The shared transition primitive animates scene entry and exit while the spatial session remains mounted, and the mod-aware loader supplies the selected portrait PNGs with a text fallback when portrait assets are unavailable.

Manual desktop and Android landscape playtesting remains required before #404 is complete. The #405 interaction presentation includes the animated radial wheel with responsive crowded-target layout and eased selection feedback, reusable scene-root transitions, and the close-up two-character dialogue scene with composited portrait layers. The project owner has manually play-tested this work and confirmed it behaves as intended; the player-portrait and target-first prompt refinements complete the remaining #405 feedback. The first authored spatial-discovery slice now covers Old Shrine with the Black Altar and Fresh Soot points of interest. Physical passages now invoke the existing graph-travel rules and transition directly into connected destination maps without leaving spatial mode. The current map and character session are persisted before travel; destination maps are restored from world state or generated lazily on first arrival. The spatial HUD now places Investigate beside Interact only while an active threat belongs to the current location, then opens the existing Combat screen through `bevy_combat::begin`; the spatial frontend does not create a separate threat or combat ruleset. Spatial time presentation now reuses the authoritative 12-part world clock and existing mod-aware sun/moon artwork in a compact horizon indicator with a 24-hour readout. Dawn and dusk add restrained warm colour washes, while night adds a restrained cool/dim wash beneath the spatial HUD; the same day/time state drives both the cue and the environment. New character creation, inheritance, and successful save loading now enter spatial exploration directly. Character record regression coverage verifies that all five tabs and nested detail/journal Back paths retain the spatial invoking context. Frontier-region creation, known-route fast travel, expanded room topology, additional authored layouts, and room-aware camera transitions remain future work under #365. Richer multi-step clue chains, evidence collection, investigation outcomes, and dynamic encounter integration also remain future work.

Keep the existing world model, quests, time, narrative, and location-level actions authoritative. Spatial exploration should progressively become the primary gameplay shell without replacing those systems; see #421 for the staged dashboard migration. Real-time spatial combat and audio remain outside this milestone.

Related design issues: #228, #229, and #252.

## Longer-term direction

Continue modularizing the codebase by responsibility rather than by file size alone. Keep runtime state, content loading, gameplay actions, presentation, persistence, and event processing independently understandable and testable.

The product direction is a character-focused, graphics-first spatial RPG backed by a persistent simulation. Spatial exploration is being delivered incrementally; real-time spatial action combat and audio integration remain future work, not current milestone claims. Keep world systems character-centred rather than turning them into remote grand-strategy management. Desktop and mobile support, hybrid input, scalable visual/simulation quality, offline single-player, player-controlled updates, and robust save/mod compatibility remain guiding constraints. See the [design principles](docs/design-principles.md).

Major gameplay work should remain data-driven where practical, preserve backward compatibility, and include focused tests for behavior affected by the change.

## Release distribution

GitHub Release publishing can optionally mirror all five desktop builds and three Android APKs to itch.io through Butler. The Android release workflow waits for the complete set of release assets before uploading them to their corresponding platform/architecture channels. Enable the mirror by configuring the repository Actions variable `ITCHIO_TARGET` and secret `BUTLER_API_KEY`; without both values, GitHub Release publishing continues without the itch.io upload.
